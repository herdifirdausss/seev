# Runbook: Merchant-Facing Owner-Service Outage (Ledger/Payin/Payout)

> [Documentation home](../../README.md) · [Operations](../README.md) · [Runbooks](README.md)

> **Status: Current. Audience: operators.**

**Symptom:** merchant transfer, pay-in, or payout requests start failing
or timing out because Ledger, Payin, or Payout — the owner services
Gateway's merchant surface calls into — are unreachable or unhealthy.
This is the merchant-scoped counterpart of each owner service's own
existing outage handling; nothing here duplicates their own runbooks
(e.g. [ledger-integrity-alert.md](ledger-integrity-alert.md)), it covers
what's specific to the merchant/B2B path on top.

## Understand the blast radius

Gateway's `services/gateway/internal/merchant` module talks to:

- **Ledger**, via `contracts/clients/ledger.Client` over gRPC (account
  provisioning: `ProvisionMerchant`, `GetMerchantAccount`,
  `ListMerchantTransactions`, and the `merchant_transfer` processor for
  P2P-style transfers between merchant-owned accounts).
- **Payin/Payout**, via the same owner-service gRPC clients Gateway
  already dials for end-user traffic (`services/payin/internal/payin/merchant.go`,
  `services/payout/internal/payout/merchant.go`) — merchant pay-in/payout requests share
  the SAME underlying connections as end-user requests to those services;
  there is no separate merchant-only connection to fail independently.

A Ledger/Payin/Payout outage therefore affects merchant AND end-user
traffic simultaneously through the shared gRPC connection — this is not
a merchant-isolated failure mode. Confirm the scope first: if end-user
traffic through the same owner service is ALSO failing, this is that
owner service's own incident (follow its own runbook); if ONLY merchant
traffic is affected, the problem is more likely in `services/gateway/internal/merchant`'s
own request path (routing rules for `sandboxVendor`, environment
mismatches) than the owner service itself.

## Diagnose

1. Check the owner service's own health:
   ```bash
   docker compose ps ledger-service payin-service payout-service
   curl -k --cacert deploy/certs/ca.pem --cert deploy/certs/dev-operator.pem --key deploy/certs/dev-operator-key.pem https://localhost:<internal-port>/ready
   ```
2. Check Gateway's own gRPC dial health — `services/gateway/cmd/gateway/main.go` dials
   Ledger/Payin/Payout once at startup with `grpcx.Dial`; a transient
   network blip is usually retried by gRPC's own backoff, but a
   long-lived TLS/identity failure requires a Gateway restart to
   re-establish (check `internal/platform/security/tls` certificate expiry if the outage
   coincides with a cert rotation window — see
   [cert-rotation.md](cert-rotation.md)).
3. Check `merchant_idempotency_records` for a spike in `'processing'`
   rows with `expires_at` approaching — that's the visible symptom of
   requests hanging against an unreachable owner service (see
   [merchant-idempotency-stuck.md](merchant-idempotency-stuck.md) for the
   general stuck-lease mechanism; this is that mechanism triggered
   specifically by an owner-service outage rather than a Gateway crash).

## What idempotency protects against here

4. **A merchant retry during the outage is safe.** Every merchant-facing
   write path (`merchant_transfer`, merchant pay-in/payout creation) is
   idempotency-gated (T4) BEFORE the owner-service call is made — a
   request that times out mid-flight leaves its idempotency record
   `'processing'` with a lease; a retry with the SAME `Idempotency-Key`
   either replays the original (now-completed, if it actually succeeded
   despite the client-side timeout) response, or takes over the expired
   lease and tries again. **This is exactly why merchants should always
   retry with the same idempotency key during an owner-service outage,
   never a new one** — a new key would risk a genuine double-submission
   once the owner service recovers and both the original AND the retried
   request happen to succeed.
5. Do not manually resubmit a merchant's request on their behalf using a
   fabricated idempotency key — you do not have visibility into what key
   their own client already used, and guessing wrong creates exactly the
   double-submission risk step 4 is designed to prevent.

## During the outage

6. Merchant requests will fail with `503`/timeout/`5xx` from the owner
   service, surfaced to the merchant as whatever error code
   `services/gateway/internal/merchant`'s own handlers map a downstream gRPC failure to
   (an owner-service-unavailable class of error, not a merchant-caused
   `4xx`). Confirm the merchant's own retry behavior matches step 4's
   guidance if they ask.
7. Webhook deliveries for events that WOULD have been generated by
   requests that never completed simply never get created — there is
   nothing to "catch up" on the webhook side once the owner service
   recovers; the underlying transaction either completed (and its event
   was already queued normally) or never happened (nothing to notify
   about).

## Recovery

8. Once the owner service is confirmed healthy, watch
   `merchant_idempotency_records` `'processing'` count return to its
   normal baseline as retries land, and confirm via a synthetic sandbox
   transaction that the full merchant path (auth → quota → idempotency →
   owner-service call → response) works end to end before declaring the
   incident resolved.
